# KB-0013 | 引入 Session 后 TUI 自然输入退化为纯对话，未稳定触发任务创建

## 1. 缺陷概述

- **缺陷编号**：KB-0013
- **发现阶段**：联调/端到端验证
- **当前状态**：✅ 已修复（已通过定向测试、CLI 测试与构建验证）
- **严重级别**：High（核心能力退化）
- **优先级**：P0

## 2. 背景与问题陈述

系统在引入 Session 概念后，TUI 输入自然语言时经常表现为普通聊天响应，未稳定进入“意图分析 → 目标创建（Goal）→ 调度执行（Scheduler）”链路，导致产品从“可执行 Agent”退化为“聊天工具”。

该问题直接影响主路径：`pb` 交互输入驱动任务执行。

## 3. 影响评估

### 3.1 业务影响
- 用户无法稳定通过自然语言创建可执行任务，核心价值受损。
- 任务驱动链路（Goal/WorkItem/Run）数据稀缺，影响可观测性与追踪。

### 3.2 技术影响
- 会话层决策（`decision`）与任务桥接（`taskInfo.goalId`）出现行为漂移风险。
- 缺少关键回归用例会导致后续演进再次退化。

## 4. 复现步骤

1. 启动 `gateway` 与 `scheduler`（均为可用状态）。
2. 启动主 TUI：`pb`。
3. 在输入框输入具备可执行意图的请求（如“请实现 X 并运行测试”）。
4. 观察结果：系统可能返回普通对话文本，但未出现可追踪任务（`goalId`）与执行状态推进。

## 5. 期望结果

对于可执行请求，系统应遵循 Session-First 契约，稳定返回：

- `decision = goal_created`
- `taskInfo.goalId` 非空
- Goal 被写入并进入 scheduler 执行链路

对于信息不足请求，应明确返回 `clarification_requested`，而不是误降级为闲聊。

## 6. 根因分析（RCA）

### 根因 1：状态机对“可执行问题句”判定过度依赖粗粒度 intent

在会话状态机中，`question` 默认映射到 `chatting`。即使上游分析结果已给出 `purpose.isActionable = true`，仍可能因为 intent 为 `question` 而不进入 `executing`，导致仅返回对话结果。

### 根因 2：回归保护不足

现有测试覆盖了：
- `clarification_requested`
- `goal_created`（task_request 场景）

但缺少“**actionable question** 仍应创建任务”的回归用例，以及 TUI Session-First 路径下 `goal_created -> Task queued UI 状态` 的验证。

## 7. 修复目标

1. 修复状态机决策，优先采用 `purpose.isActionable` 作为执行判定信号。
2. 补充回归测试，覆盖 Session-First 下的关键退化场景。
3. 将本缺陷文档升级为工程管理格式，固化后续验收与防漂移机制。
